# UI-Test System Prompts — The Test Answers Them, and Proves It Did

A permission prompt is presented by Springboard, not by the app: it covers the app, so every
query for an app element fails until it is answered. There are dozens of them — camera,
microphone, photos, contacts, calendar, reminders, location, notifications, Bluetooth, local
network, motion, speech recognition, tracking, health, media library, Siri, and more with each
OS — and any capability a suite exercises can raise one on first use.

Asking a human to tap is not a solution: the first run on any new device, a reset device, or CI
fails the same way. The suite answers its own prompts.

## `addUIInterruptionMonitor` does not receive a system prompt

Apple's documented mechanism is `addUIInterruptionMonitor(withDescription:handler:)`, whose
handler receives the interrupting element and returns whether it handled it. It still works for
an alert **your own app** presents. It does not work for a system prompt, and the distinction is
Apple's own: a Developer Tools engineer confirmed on the developer forums (November 2023, iOS 17)
that alerts generated by Springboard are not delivered to the interruption handler while alerts
generated by the app still are. It was still true when measured on iOS 27 with Xcode 27.

Two properties matter, and the second is the one that bites:

- The monitor only runs when an interaction finds the app blocked, so registering it is not
  enough — the test must interact afterwards to give it its chance.
- For a Springboard alert the handler is never called at all. XCTest detects the interruption and
  then fails to hand it over, logging:

  ```
  Failed to construct element query matching interruption. Interrupting element Alert,
  foreground application Application 'com.apple.springboard', element application: (null).
  If your test failed after this unhandled interruption, please file a bug…
  ```

  The test then fails exactly as if no monitor existed. `element application: (null)` is the
  framework failing to resolve the application that owns the alert — the element it would have
  had to hand the handler, which is why no query of yours appears anywhere in this.

  Rule out your own ordering before concluding you have hit this, because getting it wrong
  produces an identical symptom: register the monitor before the app launches, and prove the
  alert is on screen with a Springboard query before the test touches the app. With both
  guaranteed, and the prompt raised after launch returned rather than during it, the handler
  still never ran on any attempt while the same alert stayed queryable through Springboard in
  the same run.

Address the prompt where it lives instead. Springboard is an ordinary application proxy, and
its alerts are ordinary elements:

```swift
/// Answers a system permission prompt by tapping one of `accepting`, in order of preference.
/// Returns false when no prompt was up — which is normal once the permission is decided.
@MainActor @discardableResult
func answerSystemPrompt(accepting labels: [String], timeout: TimeInterval = 10) -> Bool {
    let springboard = XCUIApplication(bundleIdentifier: "com.apple.springboard")
    let alert = springboard.alerts.firstMatch
    guard alert.waitForExistence(timeout: timeout) else { return false }
    for label in labels where alert.buttons[label].exists {
        alert.buttons[label].tap()
        return true
    }
    let seen = alert.buttons.allElementsBoundByIndex.map(\.label).joined(separator: ", ")
    XCTFail("Unhandled system prompt; its buttons were: \(seen). Add the label this test needs.")
    return false
}
```

Call it where the prompt is expected — after launch for a capability the app touches at
startup, after the action that first uses the capability otherwise. Keep the helper and its
label lists in the single `XCUIApplication` extension that holds the suite's other test-side
literals (`ui-test-hierarchy-portability.md`).

## The caller names the option it needs, and never a position

Prompts do not share one affirmative answer, and several offer more than one with materially
different meanings: location offers a one-shot grant alongside a while-using grant and
sometimes an always grant, and only one of them stops the prompt returning on the next launch;
tracking's two buttons both dismiss the alert and only one grants. "Tap something affirmative"
is therefore not a specification — the test says which outcome its scenario requires, and a
suite that needs a grant to persist must not accept the one-shot answer.

Never select by index or position (`buttons.element(boundBy: 1)`, "the last button"). The
layout is not stable across prompts or OS versions, and **a wrong tap denies the permission
persistently**: the app is then dead on that device until someone resets privacy by hand, and
the failure surfaces much later as a capability that silently never works. When no expected
label is present, tap nothing and fail with the labels that were on screen — the fix is one
string, and an unrecognised prompt is a far better outcome than a silently denied one.

Labels are localized, so pin the language the suite runs in or list the labels for every
language it runs in.

## Prove the handling works: a decided permission hides the bug

A run on a device where the permission is already decided passes **without executing the
handling at all** — no prompt appears, the guard returns, everything is green. That green is
worth nothing, and it is the state every suite drifts into after its first manual run.

Reset the permission, watch the test fail without the handling, then pass with it:

```sh
# Device: uninstalling clears the app's privacy grants; the test run reinstalls it.
xcrun devicectl device uninstall app --device <udid> com.example.myapp

# Simulator: reset one service, or all of them.
xcrun simctl privacy booted reset all com.example.myapp
```

`simctl privacy` names only the services it lists in its own help — run it with no arguments to
see them. Several common prompts, camera among them, are not in that list, so `all` is the
general lever rather than a service name you assume exists.

Then confirm from the run log that the tap actually happened (`Tap "Allow" Button`) rather than
inferring it from a green result. This is the same discipline as any negative control
(`workflow/assertions-must-be-falsifiable.md`): the claim that a prompt is handled is worth
exactly what the run where it was not handled proves.
